## Context

The Jobs page is `/runs` (`/jobs` 303-redirects to it). Its run grid renders
once per page load: a running row's status chip, stage-progress chip (#475),
and TOOK column are all "as of page load", and the operator must reload to see
a run finish. The pipeline progress strip above the grid already self-polls
(15s active / 60s idle), so the strip and the rows visibly disagree within
seconds of a stage transition. The #475 plan deliberately deferred per-row
polling; #496 is the follow-up that adds it, scoped to rows that can change on
their own.

Issue #496 acceptance criteria:
- Running/queued rows auto-update status, current stage, and elapsed time
- Polling stops on terminal status (completed, failed)
- Completed rows fade-highlight briefly on transition
- No polling on already-terminal rows (no wasted requests)
- Page with zero running rows makes zero poll requests (read as: zero
  `/runs/live-rows` requests; the strip keeps its own existing 60s idle poll,
  which this change does not touch) (review)

## Design

### One poller per page, not one per row

The issue proposes per-row polling. That costs one request per live row per
tick: a watch-folder drop of 30 files queues 30 rows, so a 5s per-row poll is
6 requests/s, each recomputing the dashboard read model for the stage chip.
Instead, a single hidden poller element owns the page's live rows and swaps
each changed row into place with htmx out-of-band swaps (bundled htmx 2.0.6):

```html
<div id="runs-live" hidden
     hx-get="/runs/live-rows?ids=<uuid>,<uuid>,..."
     hx-trigger="every 5s"
     hx-swap="outerHTML"></div>
```

The fragment response is the poller itself (re-rendered with the ids that are
still live, and with `hx-get`/`hx-trigger` only when that list is non-empty)
followed by one `<div class="gt-row" id="run-row-<uuid>" hx-swap-oob="true">`
per requested run that still exists. The OOB rows are top-level siblings of the
poller, never wrapped in a container (htmx extracts OOB nodes first and swaps
the single remaining top-level element into the target). (review)

When every requested run has left the live set, the poller re-renders without
`hx-get`/`hx-trigger`, so polling stops on its own: the same self-stopping
pattern as `_progress_strip.html`, `run_assets.html`, `run_translation.html`,
and `research.html`.

Properties:
- Zero live rows on the page: the poller is not rendered, so zero
  `/runs/live-rows` requests.
- One request per tick regardless of how many rows are live; the dashboard
  read model is computed once per tick, as the strip does.
- A run that reaches `completed`, `failed`, or `cancelled` is swapped once
  more with its terminal rendering (Review link or Retry form, final TOOK for
  completed/failed, needs-review chip) plus class `is-just-finished` for the
  fade highlight, then dropped from the id list. `paused` and
  `awaiting_adjudication` also drop out of the live set but get no highlight.
  (review)
- A run that is deleted or archived mid-poll is simply not returned and is
  dropped; its last rendering stays.
- The client carries the id list (rather than the server re-deriving "all
  live runs") because that is the only way to deliver the one terminal render
  without server-side per-tick memory, and it keeps the poll scoped to the
  rows actually on the page (pagination, search, filters). Consequences, all
  intended: runs queued after page load appear on reload; on a filtered page
  (`?status=running`) a finished row stays visible in terminal form until
  reload.
- Interval: `every 5s` while any requested run is `running`, `every 15s`
  when the live set is queued-only. Same adaptive idea as the strip.
- Cap: the page emits at most `RUNS_LIVE_ROWS_MAX = 100` live ids (the
  newest, since the grid is newest-first) and the endpoint rejects more with
  400. `runs_page_size` may be configured up to 500 and 500 UUIDs would push
  the request line past uvicorn's 16 KB event limit; 100 canonical UUIDs is
  3.7 KB. Rows beyond the cap refresh on reload. This is a protocol bound,
  not operator config, so it is a module constant, not a setting. (review)

"Live" means `status in (queued, running)`. `paused` and
`awaiting_adjudication` change only through operator actions; cross-tab
staleness for those is out of scope and cheap to add later by widening the set.

The "Failed" tab renders through the grouped path and is never live, so the
poller is emitted only on the non-grouped path. The archived view
(`?archived=1`) does not build the dashboard and has no live rows; no poller.

### Row macro becomes a shared partial

`run_row` is a Jinja macro defined inline in `runs.html` (lines 175-235). Both
the page and the fragment need it, so it moves verbatim to
`legacy_runs/_run_row.html` and is imported with
`{% from "legacy_runs/_run_row.html" import run_row %}` in both templates.
Plain Jinja imports carry no caller context, so (review):
- `_run_row.html` imports `chip` and `needs_review_chip` from
  `fragments/_chips.html` itself.
- `now` and `csrf_requeue` (context variables the inline macro reads today at
  `runs.html:209` and `:216`) become explicit macro parameters, passed by both
  callers. Explicit beats `with context` here because the fragment context is
  tiny and the dependency stays visible.
- Signature: `run_row(it, progress, now, csrf_requeue, oob=false,
  just_finished=false)`. `oob` adds `hx-swap-oob="true"`; only the fragment
  sets it, so the page never emits OOB attributes. `just_finished` adds class
  `is-just-finished`.
- The main `gt-row` div gets `id="run-row-{{ it.run_id }}"` (the OOB target).
  The snippet sub-row (search results only) keeps no id; the fragment carries
  no `q`, so it never emits a snippet row and the page's snippet sibling is
  untouched by the swap.
- Copy: the running-row TOOK tooltip and the stage-chip tooltips change from
  "as of page load" to "as of last refresh".

### Fragment endpoint

`GET /runs/live-rows` in `legacy_runs.py`, registered next to
`runs_progress_strip` (around line 838) and therefore before
`/runs/{run_id}` at line 1109 (review). Same `OperatorDep` + `SessionDep`,
same `Cache-Control: no-store`. Steps:
1. Parse `ids` (comma-separated canonical UUIDs); dedupe preserving order;
   400 on a malformed id or more than `RUNS_LIVE_ROWS_MAX`. Empty or absent
   `ids` short-circuits to the stopped poller without touching the DB.
2. `list_runs(session, run_ids=ids, status=None, review=None,
   lifecycle=None, cursor=None, page_size=len(ids), archived=False,
   gates=gates_from_settings(settings))`. New optional parameter on
   `list_runs` in `runs_query.py`: `run_ids: Sequence[uuid.UUID] | None =
   None`, applied as `PipelineRun.id.in_(run_ids)` when `run_ids is not
   None` (an empty list means no matches, `None` means unrestricted), placed
   after the archive/lifecycle/status/review/search predicates and before the
   keyset clause. No other predicate changes. (review)
3. Stage progress for running items exactly as `/runs` computes it: extract
   that block (`legacy_runs.py:706-725`) into
   `_stage_progress_for(items, dashboard, now)` and call it from both routes.
   `pipeline_dashboard_state` is computed once per tick, as in the strip.
4. Render `legacy_runs/_live_rows.html` with `items`, `stage_progress`,
   `live_ids` (items still queued/running), `poll_seconds`, `now`,
   `csrf_requeue`, and `finished_ids` (items now completed/failed/cancelled).

### Page wiring in `runs.html`

- Import the macro from the partial; delete the inline definition; pass
  `now` and `csrf_requeue` at both call sites (grouped singleton at line 277,
  standard loop at line 283).
- The `/runs` route adds `live_ids` (page items with status queued/running,
  newest-first, capped at `RUNS_LIVE_ROWS_MAX`) and `poll_seconds` (5 if any
  running else 15) to the context. (review: `poll_seconds` was missing)
- After the grid, on the non-grouped path and only when `live_ids` is
  non-empty, render the poller via a small `poller` macro in
  `_live_rows.html` so the page never duplicates rows. The `{% if dashboard
  %}` timer script is unchanged.

### CSS (in `base.html`, next to the row state tints at line 983)

```css
@keyframes gt-row-finished { from { background: var(--accent-soft); } to { background: transparent; } }
.gt-row.is-just-finished > * { animation: gt-row-finished 2.5s ease-out; }
@media (prefers-reduced-motion: reduce) { .gt-row.is-just-finished > * { animation: none; } }
```

The row is `display: contents`, so the animation goes on the cells, matching
how the state tints are applied. Neutral accent, not `--ok-soft` (green would
mislabel a failed run; the chip already carries the outcome colour). (review)
Reduced motion shows no highlight rather than a permanent tint. The class is
present in the inserted markup, so the animation starts on insertion with no
script. A small end-of-animation step back to the needs-human tint (alpha
.04) is acceptable.

### No feature flag

Existing page polling (the strip) has no flag; this is presentational,
authenticated, and self-limiting. Both reviewers agree.

## Tests (TestClient + string assertions, existing `_make_run` helpers)

Page (`/runs`):
1. Only completed/failed runs: no `id="runs-live"`, no `/runs/live-rows`.
2. One running + one completed: poller present, `ids` contains only the
   running run, `every 5s`. Queued-only: `every 15s`.
3. `?view=failed` and `?archived=1`: no poller.
4. Every run row (not group summary or aux-job rows, which are also
   `gt-row`) carries `id="run-row-<uuid>"`; no `hx-swap-oob` anywhere on the
   page. (review: scoped)
5. Search page with a snippet: the snippet sibling renders once, unchanged.

Fragment (`/runs/live-rows`):
6. `ids=<running>`: poller with `hx-trigger`, row with `hx-swap-oob="true"`
   and `pill running`, no `is-just-finished`; stage chip text present when
   the run has a current stage and a stage row; TOOK present.
7. Mixed set: one completed (unresolved label) + one running: both rows
   render, completed row has `is-just-finished`, needs-review chip, Review
   link; only the running id remains in the next `hx-get`.
8. Failed: row has `is-just-finished` and the Retry form with the right
   `revision` and a CSRF token. Cancelled: `is-just-finished`, TOOK shows "—"
   (the elapsed CASE covers completed/failed only; not extended here).
9. Paused or awaiting_adjudication: row re-renders, no highlight, dropped
   from the live set; poller stops when nothing else is live.
10. Running-only set flips to queued-only: interval becomes 15s.
11. Deleted/archived id: no row emitted, id dropped. Duplicate ids: one row.
12. Malformed id → 400; more than `RUNS_LIVE_ROWS_MAX` → 400; empty `ids` →
    stopped poller and no DB query; unauthenticated → same status as
    `/runs/progress-strip`.

Query:
13. `list_runs(run_ids=[a, b])` returns exactly those runs regardless of
    status; `run_ids=[]` returns nothing; composes with `archived=True`.
